# Project Delta - 9일차 개발일지

## 개발 주제

**최근 3개 백업 보존·복원 로직과 강제 종료·비정상 종료 후 런 복구 흐름 구현**

8일차의 원자적 저장·체크섬 검증 위에, 기획서 9.5절 "자동 백업"과 "강제 종료 복구"를 구현했다. 백업 슬롯을 1개에서 3개 순환으로 확장하고, 파일이 손상됐을 때 자동으로 다음 후보를 시도하는 복구 순회 로직을 추가했다.

---

## 개발 목표

- 백업을 Backup1(직전)/Backup2/Backup3(세 번째 이전) 3단계로 순환 보관
- 저장 시점마다 오래된 백업을 밀어내는 로직 구현
- 강제 종료 후 재실행 시 현재 파일 → 임시 파일 → Backup1~3 순서로 자동 복구
- "백업은 손상 복구 전용이며 플레이어가 과거 시점으로 되돌리는 용도가 아니다" 원칙 유지

---

## 구현 내용

### 1. 백업 경로 확장

```text
SavePaths.GetBackupPath(target, slot)
→ {target}.bak1, {target}.bak2, {target}.bak3
```

8일차까지는 `.bak` 슬롯 1개만 있었다. 오늘부터 슬롯 번호를 받아 세 경로를 만들 수 있다.

---

### 2. 저장 시 백업 순환

```text
저장 직전:
Backup2 → Backup3로 복사
Backup1 → Backup2로 복사
↓
File.Replace(임시 파일, 현재 파일, Backup1 경로)
→ 현재 파일 → Backup1로 이동 + 임시 파일로 교체를 원자적으로 한 번에 처리
```

밀어내기를 반드시 `File.Replace` **이전에** 먼저 실행해야 한다 — 순서가 바뀌면 최신 백업이 밀려나기 전에 덮어써져 유실된다.

결과적으로 매 저장마다 다음처럼 갱신된다.

```text
Backup1 = 직전 정상 저장
Backup2 = 두 번째 이전 정상 저장
Backup3 = 세 번째 이전 정상 저장
```

---

### 3. 강제 종료 복구 순회

기획서 9.5절 표를 그대로 순서로 옮겼다.

```text
현재 파일 정상          → 그대로 사용
현재 파일 손상 + 임시 파일 정상 → 임시 파일로 복구
현재 파일·임시 파일 손상 → Backup1 확인
Backup1도 손상          → Backup2 확인
Backup2도 손상          → Backup3 확인
전부 손상               → 복구 실패 예외
```

8일차에 만든 체크섬 검증(`TryReadEnvelope`)을 그대로 재사용해서, 다섯 개 후보를 순서대로 시도하다가 처음으로 검증에 성공하는 파일을 사용한다.

---

### 4. 백업 사용 원칙 유지

기획서 9.5절 제약(*"플레이어는 백업을 선택해 이전 선택, 전투 결과, 보상과 엔딩으로 돌아갈 수 없다"*)에 따라, 백업을 사용자가 직접 고르는 UI나 API는 만들지 않았다. 복구는 오직 현재 파일이 손상됐을 때 자동으로만 일어난다.

---

### 5. 호출부는 변경 없음

`ReadProfile()`/`ReadRun()`/`ReadSettings()`의 이름과 반환 타입이 그대로 유지되어, 복구 로직이 내부로 숨어 들어가도 `AppRoot.cs`는 수정할 필요가 없었다.

복구가 실제로 일어나면 현재는 `Debug.LogWarning`으로만 남긴다. 팝업 안내 문구(*"저장 데이터에 문제가 발견되어 최근 정상 데이터로 복구했습니다"*)는 UI 시스템이 생기는 이후 일차에 연결한다.

## 최종 확인 항목

9일차 완료 기준은 다음과 같다.

- Unity 컴파일 오류 없음
- 저장을 3번 이상 반복하면 Backup1/2/3 세 파일이 모두 정상적으로 갱신됨
- 현재 파일을 강제로 손상시켜도 Backup1로 자동 복구됨
- Backup1까지 손상돼도 Backup2, Backup3로 순서대로 시도함
- 모든 후보가 손상된 경우 명확한 예외를 던짐
- 백업을 선택하는 별도 UI/API가 존재하지 않음
